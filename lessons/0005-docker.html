Docker: the sealed room Palworld lives in

Palworld doesn’t run loose on your server. It runs inside a container, a sealed room with everything it needs. By the end you’ll be able to read your Palworld settings file line by line, and explain why companies package nearly all their software this way.

Warm-up · from Lessons 01–04

Part 1 · The problem Docker solves

Installing software the old way is messy. A program needs the right versions of dozens of other pieces, and two programs on the same server can need different versions and break each other. People used to say: “It works on my computer!” Then it didn’t work on the server.

Docker fixes this by packing a program together with everything it needs into one sealed package. Docker’s own definition of a container: “an isolated process with all of the files it needs to run.”1 (A process is just a running program.) The same package runs the same way on your laptop, on Oracle, or on Amazon.

In the condo comparison

Your server is the building. A container is a sealed, self-contained room inside it, with its own furniture (software), its own private address, and only the doors you choose to connect to the outside. Palworld lives in a room called palworld, and its private address inside the server is 172.18.0.2. Remember the 172. private range from Lesson 02? This is it.

Container or virtual machine?

Your Oracle server is itself a virtual machine (VM): a whole pretend computer, with its own complete operating system, carved out of a much bigger real one. A container is lighter. It doesn’t carry a whole operating system; it shares the server’s. That’s why you can run many containers on one server.1 VM = a whole house; container = a room inside one.

Part 2 · Image and container

Two words you must not mix up:

  • An image is the packed kit: the blueprint plus all the materials, frozen and ready to use. Yours is thijsvanloef/palworld-server-docker (about 2 GB), made by a community developer and downloaded from Docker Hub, a public library of images.2
  • A container is a room actually built from that kit, and running. One image can be used to build many identical containers.

Updating works by building a fresh room from the newest kit: throw away the old container, start a new one. That sounds scary for a game world, until you meet volumes (Part 4).

Part 3 · The compose file: your written order form

Instead of typing a long command to start the container, you write the instructions down once in a file. That’s Docker Compose, and the file is /opt/palworld/docker-compose.yml.3 Writing setup down in files instead of clicking or typing it each time is a core DevOps habit, often called “configuration as code”. Here’s yours, shortened, with passwords hidden:

services:
  palworld:
    image: thijsvanloef/palworld-server-docker:latest   # which kit to build from
    container_name: palworld                            # the room's name
    restart: unless-stopped                             # if it crashes or the server reboots, start it again
    ports:
      - 8211:8211/udp                                   # building door 8211 → room door 8211, UDP
    environment:                                        # settings handed to Palworld
      SERVER_NAME: "Palhaven"
      PLAYERS: 16
      SERVER_PASSWORD: "********"
      BACKUP_CRON_EXPRESSION: "45 4 * * *"              # back up at 4:45 every day
      AUTO_REBOOT_CRON_EXPRESSION: "55 4 * * *"         # restart at 4:55 every day
    volumes:
      - ./data:/palworld                                # world save kept OUTSIDE the room

The file format is called YAML. It’s a list of name: value settings, and the indentation (spaces at the start of a line) matters: it shows what belongs to what. One wrongly indented line can break the whole file, and that’s a classic real-world mistake.

The 45 4 * * * style is called a cron expression: minute 45, hour 4, every day, every month, every weekday. You’ll meet cron again in Lesson 07.

Part 4 · Two doors out of the room: ports and volumes

Port mapping (ports:). The room has its own address, 172.18.0.2, which the internet can’t reach. The line 8211:8211/udp tells Docker: “anything arriving at the server’s port 8211 over UDP, forward it to the room’s port 8211.” Docker sets up the forwarding automatically, and keeps every port you didn’t list blocked.4 This is another NAT, like the receptionist from Lesson 02.

Volume (volumes:). Anything saved inside a container disappears when the container is thrown away. So the world save isn’t kept in the room. It’s kept in a storage room outside, /opt/palworld/data on the server, connected to the container’s /palworld folder. When the container is replaced during an update or a settings change, the world stays put.

Say it yourself first, then open this

“Palworld runs in a Docker container: a sealed room with everything it needs, sharing the server’s operating system. It’s built from an image, the packed kit. The compose file is the written order form: which image, the restart rule, the settings, the port mapping that forwards server port 8211 UDP to the container, and a volume that keeps the world save outside the container so it survives updates.”

Practice 2 · Look inside Docker (10 min)

All of these only look. Don’t run docker compose up or restart here: real players may be online.

  • ssh gameserver
  • sudo docker ps: running containers. Find palworld, its STATUS (Up … (healthy)) and PORTS.
  • sudo docker images: the kits downloaded onto the server, and their size.
  • sudo docker port palworld: the port mapping, straight from Docker.
  • sudo docker stats --no-stream: how much CPU and memory the room is using right now.
  • sudo docker logs --tail 20 palworld: the last 20 lines of Palworld’s diary. Lines with BOX64 are normal noise.
  • sudo ls /opt/palworld/data: the storage room (volume). Then sudo ls /opt/palworld/data/backups to see the daily backups. exit.
  • Explain it. Out loud: image vs container, and what the ports: and volumes: lines do.
