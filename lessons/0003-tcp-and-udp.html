Two ways to send data: TCP and UDP

In Lesson 01 you could knock on port 22 from your laptop, but the same test can’t check Palworld’s port 8211. That’s because data travels in two different styles. Once you know them, you can read the list of every program waiting for visitors on your server.

≈ 25 minBuilds on Lessons 01–02Nothing here can break the server

Warm-up · from Lessons 01–02

Part 1 · Data travels in small pieces

Data doesn’t travel as one big lump. It’s cut into small pieces called packets, and each one carries the address and port it’s going to. When you move in Palworld, your laptop sends a stream of small packets saying “I’m here now… now here… now here.”

How those packets are sent follows a set of rules called a protocol. Two protocols handle almost everything: TCP and UDP. The port number is written inside the TCP or UDP part of each packet. That’s how the server knows which program it’s for.1

Part 2 · TCP: the registered courier

TCP (Transmission Control Protocol) works like a registered courier with signatures:

  • Before sending anything, both sides say hello and agree to talk. This is called a handshake, and together they form a connection.
  • Every packet is confirmed (“got it”). Anything lost gets sent again.
  • Packets are put back in the right order at the other end.

It’s reliable, but all that checking takes a little extra time. TCP is used whenever every piece must arrive: websites, email, downloads, and SSH. If one letter of your command went missing, sudo docker ps could turn into something else entirely.

Part 3 · UDP: shouting updates across a room

UDP (User Datagram Protocol) just sends. There’s no handshake, no “got it”, no resending. It’s like calling out the score during a basketball game: if someone misses one shout, it doesn’t matter, because the next one is coming a second later and is more up to date anyway.

That’s exactly what a game needs. If a packet saying “a player is at spot A” arrives late, it’s useless, because you’re already at spot B. Waiting to resend it would only cause lag. So Palworld uses UDP, as do voice calls and live video.

So that’s why the knock test failed on 8211

Test-NetConnection knocks the TCP way: it tries a handshake. Palworld listens for UDP, and UDP never answers a handshake, so the test can’t tell whether 8211 is working. It’s like ringing a doorbell at a door that only takes notes slipped under it.

It also explains the firewall rules in Oracle’s settings. Each rule names a protocol and a port: “TCP 22” and “UDP 8211”. Opening TCP 8211 by mistake wouldn’t let a single player in.

Part 4 · Who is listening? And what is “localhost”?

A program that waits for packets on a port is listening. On Linux you can list every listener with one command. Here is part of what your server showed on 17 Oct 2026, tidied up:

Protocol  Address : port          Program
tcp       0.0.0.0 : 22            sshd           # SSH, open to everyone
udp       0.0.0.0 : 8211          docker-proxy   # Palworld (through Docker, Lesson 05)
udp       0.0.0.0 : 41641         tailscaled     # Tailscale, your private phone link
tcp     127.0.0.1 : 8797          python         # your monitor, inside only
tcp 100.64.0.10 : 8797         python         # your monitor, on your private Tailscale network

Two special addresses show up here:

  • 0.0.0.0 means “listen on every address this computer has”: open to visitors (if the firewall allows).
  • 127.0.0.1, also called localhost, means “this computer itself”. A program listening on 127.0.0.1 can only be reached from inside the server, like a phone extension that only rings within the building. Your monitor uses this on purpose. Its only other address is its private Tailscale one (100.64.0.10, a network only your own devices can join), never 0.0.0.0, so strangers on the internet can’t even knock on it (Lesson 07).
Say it yourself first, then open this

“Data travels in packets. TCP is like a registered courier: handshake first, every packet confirmed and resent if lost. SSH uses it because every character matters. UDP just sends, with no confirmations, which makes it faster. Palworld uses it because a late position update is useless. Firewall rules name both the protocol and the port, like UDP 8211. Localhost, 127.0.0.1, means the computer itself, so my monitor can only be reached from inside.”

Practice 2 · See the listeners yourself (10 min)

  • ssh gameserver
  • Type sudo ss -tulpn and press Enter. (ss = socket statistics. The letters mean: tcp, udp, listening, show the program, numbers instead of names. sudo runs it as administrator: Lesson 04.)
  • Find these four lines: tcp … 0.0.0.0:22 (sshd), udp … 0.0.0.0:8211 (docker-proxy), udp … 0.0.0.0:41641 (tailscaled) and tcp … 127.0.0.1:8797 (python, your monitor).
  • Notice other 127.0.0.x lines too: helper programs that only talk inside the server. Lots of listeners are normal. What matters is which ones the firewall lets visitors reach. Type exit.
  • Explain it. Out loud: why Palworld uses UDP and SSH uses TCP, using the courier and the shouting comparisons.

New words from this lesson

PacketA small piece of data carrying its destination address and port.
ProtocolAn agreed set of rules for communicating.
TCPThe reliable protocol: handshake, confirms, resends, keeps order (SSH, websites).
UDPThe fast protocol: just sends, no confirmations (games, voice, video).
HandshakeTCP’s hello exchange that sets up a connection.
ListeningA program waiting for packets on a port.
Localhost (127.0.0.1)“This computer itself”: reachable only from inside.
