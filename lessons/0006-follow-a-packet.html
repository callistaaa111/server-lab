Follow a packet: the five checkpoints

“My friend can’t connect” is the most common problem you’ll ever be asked to fix, in games and at work. This lesson follows one game packet from a friend’s laptop all the way to the game, through five checkpoints. Then you practise finding which one is broken, the way an engineer does.

≈ 35 minUses everything from Lessons 01–05Interview question: “walk me through troubleshooting”

Warm-up · from Lessons 01–05

Part 1 · A surprise: there are two guards

In Lesson 01 there was one guard, the firewall. The full truth: the server has two firewalls, and both must let a packet through.

  • Oracle’s firewall, called a security list. It lives in Oracle’s network, outside the server. You change it on Oracle’s website, not with commands. It applies to the whole subnet, the “street” from Lesson 02.1 Think of it as the guard at the village gate, who checks everyone entering the street.
  • The server’s own firewall, a Linux tool called iptables. It lives inside the server. Oracle’s Ubuntu images come with their own firewall rules,2 and the last rule says “reject everyone else”. This is the lobby guard of your building.

That’s why opening port 8211 on Oracle’s website alone didn’t work when the server was first set up: the village guard said yes, but the lobby guard still said no. Almost everyone new to Oracle Cloud trips on this.

Part 2 · The five checkpoints

  1. The road: is the server on, and does the receptionist forward to it? If the server is switched off, nothing else matters.
    Check: in Oracle’s website the server shows Running. From your laptop, Test-NetConnection 203.0.113.84 -Port 22 -InformationLevel Quiet prints True.
  2. The village gate guard (security list): does Oracle allow UDP 8211? No command on the server can see this one. You have to look on the website.
    Check: Oracle Console → Networking → Virtual cloud networks → gameserver-vcn → Security → Default Security List → a rule for UDP 8211.
  3. The lobby guard (iptables): does the server’s own firewall allow it?
    Check: sudo iptables -L INPUT -n --line-numbers. Find udp dpt:8211 with ACCEPT, above the final REJECT. (dpt = destination port.)
  4. The forwarding desk (Docker): is port 8211 mapped into the container?3
    Check: sudo docker port palworld prints 8211/udp -> 0.0.0.0:8211.
  5. Someone home: is the game running and healthy? Every door can be open, but if nobody is inside, nobody answers.
    Check: sudo docker ps shows Up … (healthy). If not, read the diary: sudo docker logs --tail 100 palworld.

Part 3 · Why go in order

Check from the outside in, 1 → 5. Each check takes seconds, and once one fails, you know where the problem is and can stop searching. It’s like tracing a dead outlet: you check the main breaker before you open the outlet box.

Two clues that point you to the right spot fast:

  • Even SSH fails → start at checkpoint 1: the server may be off.
  • It works from inside the server but not from outside → it’s one of the guards: checkpoint 2 or 3.
The 90-second interview answer: say it yourself first, then compare

“I go outside-in. First, is the server running and reachable at all? I test SSH. Second, the cloud firewall: is the port and protocol allowed in the security list? Third, the server’s own firewall, like iptables. There are two firewalls, and both must allow it. Fourth, if it runs in a container, is the port mapped from the server into the container? Fifth, is the program actually running and healthy? I check its status and logs. Each check rules out a whole layer.”

Practice 1 · Which checkpoint is broken?

Each scenario is a real kind of problem. Find the first checkpoint that fails.

Practise · safe terminal

Practise in this safe copy first: it behaves like the server, using real output captured from it. Then do the real thing below. (Checkpoint 2 lives on Oracle’s website, so you can’t check it from a terminal.)

Practice 2 · Walk the checkpoints (15 min)

  • 1 · The road. From PowerShell: Test-NetConnection github.com -Port 22 -InformationLevel Quiet → True: the server is on, and the road to it works.
  • 2 · A lobby guard you own. Get-NetFirewallProfile | Select-Object Name, Enabled: True means your laptop’s own firewall is on. If you have a cloud account, open its firewall page (Oracle: security list, AWS: security group) and find one inbound rule. Look only.
  • 3 · The server’s lobby guard. In the practice terminal above (a safe copy of a real server): ssh gameserver, then sudo iptables -L INPUT -n --line-numbers. Find the 8211 ACCEPT and the final REJECT.
  • 4 · The forwarding desk. sudo docker port palworld
  • 5 · Someone home. sudo docker ps, then exit.
  • Interview drill: set a 90-second timer and give the answer above out loud, without reading. Record it on your phone and listen back. Where you hesitate is what to review.
