How you know it’s healthy: monitoring & backups

The server tells you when something’s wrong before other players do. It sends alerts to your phone, restarts itself when memory runs low, and backs up the world every morning. In the industry, this is called monitoring and reliability, and it’s a big part of what DevOps engineers are paid for. This lesson gives you the words for what you already built.

Warm-up · from Lessons 01–06

Part 1 · Monitoring: watching the numbers

Monitoring means collecting numbers about a system over time and watching them. Each number is a metric: players online, memory used, CPU busy, server uptime. A single reading tells you little. The history tells you the story, like a power meter compared month to month.

Google’s engineers, who run some of the biggest systems in the world, suggest watching four kinds of metric first. They call them the four golden signals:1

SignalPlain meaningOn the game server
LatencyHow long a response takesLag, server frame rate
TrafficHow much it’s being usedPlayers online
ErrorsHow often things failCrashes, unexpected restarts
SaturationHow “full” it isMemory and CPU used

Part 2 · What the monitor actually does

The monitor is a small program running on the server. It checks things every 5 seconds and keeps 180 days of history in a small database. Here’s what it does, in industry words:

The monitor…Industry word
Records players, memory, CPU and uptime every 5 secondsMetrics collection
Draws charts for the last 24 hours to 90 daysDashboard
Sends a notification to your phone (through ntfy) and pop-ups on your laptopAlerting
Notices when the server restarted when it shouldn’t haveCrash detection
If PalServer uses over 14 GB of memory, or free memory stays under 2 GB for 2 minutes: warns players, saves, restartsAuto-remediation (self-healing)
Listens only on 127.0.0.1 and on its private Tailscale address (a network only your own devices can join), never on the public internetLeast exposure: nothing public that doesn’t need to be

Good alerts are rare alerts

An alert should mean “a human needs to do something now”. If your phone buzzed every time a player joined, you’d start ignoring it, and then miss the one that matters. Google’s guide makes the same point: every alert should be something you can act on.1 That’s why it makes sense to keep “player joined” notices as laptop pop-ups and save phone alerts for real problems.

Health checks

Remember Up 3 hours (healthy) in docker ps? The image has a built-in health check: Docker regularly asks the game “are you OK?” and records the answer. “Running” only means the program exists; “healthy” means it answers. That difference catches the problems where the server looks fine but nobody can join.

Part 3 · Services and schedules: things that run by themselves

The monitor runs as a service managed by systemd, the Linux part that starts programs at boot and keeps them running. Yours is set to start automatically when the server boots, and to restart 5 seconds after any crash. That’s what active (running) meant in Lesson 04.

Scheduled jobs use the cron format you saw in the compose file. Your daily routine (Manila time):

45 3 * * *3:45 AMback up the world, keep 7 days of backups
55 3 * * *3:55 AMwarn players, then restart at 4:00 (clears memory build-up and installs game updates)

Part 4 · Backups: the only thing that saves you from mistakes

A backup is a copy you can go back to. Monitoring tells you something broke; backups let you undo it: a corrupted save, a bad update, a wrong command. Three questions professionals ask about any backup plan:

  1. How much could we lose? With daily backups, up to about a day of progress. The industry name is RPO (Recovery Point Objective): the most data you can accept losing.
  2. How fast can we be back? Restoring a game backup takes minutes. That’s the RTO (Recovery Time Objective): the most downtime you can accept.
  3. Where are the copies? Your backups are in /opt/palworld/data/backups, on the same disk as the world. If that disk failed, both would be gone. A common rule of thumb, 3-2-1, says: keep 3 copies, on 2 different kinds of storage, with 1 somewhere else. Copying backups to your laptop with scp (it’s in your cheat sheet) covers the “1 somewhere else”.

One more saying worth knowing: a backup you’ve never restored is just a hope. Teams practise restoring so they know it works before they need it.

Say it yourself first, then open this

“My monitor collects metrics every 5 seconds, covering traffic (players), saturation (memory and CPU) and errors (crashes), and keeps 180 days of history. It alerts my phone only for real problems, and it auto-remediates by restarting when memory runs low. It runs as a systemd service that restarts itself. Backups run daily at 3:45 and are kept 7 days, so my RPO is about a day. To follow 3-2-1 I should also keep copies off the server.”

Practice 2 · Read real monitoring (15 min)

  • Your laptop is monitored too. Press Ctrl+Shift+Esc → Performance. Find a chart for each golden signal you can: saturation (CPU, Memory), traffic (Wi-Fi or Ethernet).
  • Leave it open and start a big download or a video. Watch traffic and saturation move. That’s what a dashboard alert would watch.
  • In the practice terminal above (a safe copy of a real server): systemctl status palworld-monitor: find enabled (starts at boot) and active (running).
  • sudo ls -l /opt/palworld/data/backups: count the backups and check the dates. That’s the retention.
  • 3-2-1 for your own files (optional): copy one folder you care about to a USB drive and to a cloud drive. Now that folder follows 3-2-1.
  • Explain it. Out loud: how you would know a server is in trouble, and how you would recover the world if it got corrupted.
